## 1. 一句话概括

Harness² 用冻结模型周围的可执行框架作为修改对象，先在当前任务上做 Propose–Probe–Compose，再把有依据的组件和改进经验留给未来任务；实验支持有限任务流内的性能提升，不构成持续自我加速或正确性保证。

## 2. 研究问题与贡献类型

贡献以系统和方法为主，附带经验评估。原文第 2 页提出两个问题，开放任务没有可靠标准答案反馈，单任务改进也未必提升下一次改进。第 3–7 页将解决方案拆为任务内框架改进和任务间改进库更新。区别于只润色答案或把上一个任务的框架直接继承。

## 4. 方法、数据和实施条件

- 原文 §2 中，执行模型固定；每个新任务从 H0 起步，任务内 improvement harness 固定，任务结束后更新库。
- 并行模式 k 个基础执行、2k 个候选试跑和 k 个合成后执行；顺序模式使用相同 4k 执行计数，并进行 k 轮连续修订。默认编辑阶段是 3k，会另计选择、反思及实际重试。
- WorkBuddy 测试集为 Code 40、Web 35、Office 25；宏平均等权领域。JobBench 为 34 个测试任务。LAB 为 100 个保留测试任务，24 个开发任务用于 Meta-Harness 离线搜索。
- 主表使用 GLM-5 与 Gemini 3.5 Flash、OpenCode 与 Codex；默认编辑器 Claude Opus 4.8。主表为三个打乱任务顺序的运行均值与标准差；图 8 另测同模型执行与编辑。
- 机制案例取自图 9，第 11–12 页，43.1 到 77.8 为作者事后评估，评分未作为改进输入。

## 5. 局限与疑点

作者在附录 F–G 明确保留额外计算、共享偏差、随机执行、经验库管理和自适应预算问题。图 14 区分错误选择、错误规则和执行或裁判变异。

额外源码观察限定到提交 `1cfe254e8d25b15f37048c3730134686abe60335`。

- `harness2/core/recursion.py` 调度与文档均注明 4k rollout、3k 改进阶段。
- `harness2/core/library.py` 仅在 `cue`、`lesson`、`evidence` 有内容时保存条目，按领域组织完整框架与经验。
- `harness2/core/selection.py::selection_pool` 仅将 k 个最终合成或检查点放入终选池，排除参考执行；不能仅根据附录通用提示词声称原始交付物总在可选范围内。
- `harness2/core/context.py` 过滤送入编辑上下文的评分相关文件和裁判结果。
- `docs/EXPERIMENTS.md#web-access` 披露公开版本不限制执行器联网，并记录 Codex 自行下载 JobBench rubric 的验证案例。此观察说明有泄漏通道，不证明论文全部实验已被污染。
- 同一实验指南将全量 LAB 列为 1,143 个任务，并要求记录 JobBench 的实际下载版本。公开默认数据和论文保留集不能混为一谈。
